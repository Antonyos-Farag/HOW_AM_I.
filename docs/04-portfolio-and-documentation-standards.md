### ✅ 5-Part Documentation Standard
My goal is **not** simply to publish answers or flags. Every technical document or write-up explains:
1. **The Investigation Process:** How the problem or incident was approached.
2. **The Reasoning Behind Each Step:** *Why* a specific hypothesis, query, or command was chosen.
3. **The Evidence Observed:** Exact log entries, packet captures, file-system artifacts, or system behaviors found.
4. **The Tools Used:** Commands, parameters, and how the tool parses or interacts with the underlying data.
5. **The Lessons Learned:** Key takeaways for detection, prevention, or deeper system understanding.

## 📚 Learning Style & Expectations

I prefer structured, technically accurate explanations that help me understand **why** something works, not just what commands to execute.

| ✅ What I Value | ❌ What I Avoid |
| :--- | :--- |
| ✔️ Step-by-step explanations with practical examples | ✖️ Exaggerated claims about abilities or shortcuts |
| ✔️ Underlying logic, mathematics, or system behavior | ✖️ Unnecessary motivational language |
| ✔️ Clear explanations of commands, tools, parameters, and outputs | ✖️ Superficial explanations that make a subject appear easier than it really is |
| ✔️ Realistic lab exercises and troubleshooting | ✖️ Blindly following instructions without reasoning |
| ✔️ Connections between theory and practical implementation | ✖️ Rushing into advanced topics before establishing prerequisites |
| ✔️ Honest feedback about mistakes, knowledge gaps, and skill level | ✖️ Treating AI/ML as ready-made black boxes |
| ✔️ Structured roadmaps built progressively on prerequisites | ✖️ Publishing flags without investigative explanations |
